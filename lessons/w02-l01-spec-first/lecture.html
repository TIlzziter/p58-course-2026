Зачем писать спеку

  • Код дорого переписывать, текст — дёшево. Ошибку в спеке исправить в 10 раз проще, чем в коде.
  • Спека — общий договор: фронтенд и бэкенд работают параллельно, не дожидаясь друг друга.
  • Агенту нужен контекст: без спеки он додумывает, и додумывает по-своему.
  • Тестировщик пишет тесты по спеке до кода.
Spec-first — это не бюрократия, а способ не спорить в пятницу вечером, «как должно было работать».
Spec-first и TDD
Спека задаёт «что», тесты фиксируют её в исполняемом виде, код отвечает «как». Порядок: спека → тесты → код → ревью по спеке.
Живой документ
Спека меняется через PR, как код. Изменение протокола без PR в docs/SPEC.md — нарушение правил команды.

Что такое user story

Как игрок, я хочу позвать друга в игру ссылкой, чтобы сыграть с ним, не ища его в лобби.
  • Кто — роль пользователя (игрок, зритель, администратор).
  • Что — действие, а не кнопка («позвать друга», а не «нажать синюю кнопку»).
  • Зачем — ценность. Без «зачем» не понять, что можно упростить.
INVEST
Хорошая история: Independent, Negotiable, Valuable, Estimable, Small, Testable. Самое важное для нас — Small и Testable.
Эпик и история
«Мультиплеер» — эпик. «Позвать друга ссылкой», «увидеть ход соперника без перезагрузки», «доиграть после обрыва» — истории.

Критерии приёмки

  • История без критериев — пожелание. Критерий — проверяемое утверждение.
  • Формат Дано / Когда / Тогда (Given / When / Then).
Пример: приглашение
Дано: игрок А создал комнату 7
Когда: игрок Б открывает ссылку t.me/p58bot/play?startapp=room7
Тогда: Б попадает в комнату 7 вторым игроком, А видит «Соперник подключился»
И: третий игрок по той же ссылке видит «Комната заполнена»

Из критерия — тест
Каждая строка «Тогда» становится assert. Если строку нельзя проверить кодом или руками за минуту — переформулируйте.

REST: ресурсы и методы

  • Ресурс — существительное: /rooms, /rooms/7, /rooms/7/moves.
  • Метод — действие: GET читать, POST создать, PUT/PATCH изменить, DELETE удалить.
  • GET не меняет состояние: его можно повторять, кэшировать, открывать в браузере.
ЗапросСмысл
GET /roomsсписок комнат
POST /roomsсоздать комнату
GET /rooms/7состояние комнаты 7
POST /rooms/7/movesсделать ход
Идемпотентность
PUT и DELETE можно повторить без вреда, POST — нет. Ход дважды из-за плохой сети — классический баг; лечится номером хода в запросе.
Плохие пути
/makeMove?room=7, /getRooms — глагол в пути. Работает, но читать и документировать сложнее.

Ошибки в одном формате

Ответ с ошибкой
{
  "detail": {
    "code": "not_your_turn",
    "message": "Сейчас ходит игрок 2"
  }
}
  • code — для программы (клиент показывает перевод), message — для человека.
  • Список кодов ошибок — в спеке, а не только в коде.
Ответ с ошибкой
{
  "detail": {
    "code": "not_your_turn",
    "message": "Сейчас ходит игрок 2"
  }
}
Как это в FastAPI
raise HTTPException(409, detail={"code": "not_your_turn", "message": "..."}). Валидацию тела FastAPI делает сам и отвечает 422.
Не выдавайте лишнего
В message не должно быть трейсбека, SQL и путей к файлам — это подсказка атакующему.

Pydantic-модели — спека в коде

api/schemas.py
from pydantic import BaseModel, Field

class MoveIn(BaseModel):
    column: int = Field(ge=0, le=6)

class RoomOut(BaseModel):
    room_id: int
    board: list[list[int]]   # 6 строк по 7, 0 — пусто, 1/2 — игроки
    turn: int                # чей ход: 1 или 2
    winner: int | None = None
  • FastAPI проверяет запрос по модели и сам отвечает 422 при ошибке.
  • По моделям строится документация /docs (OpenAPI).

Каркас FastAPI

api/main.py
from fastapi import FastAPI, HTTPException
from .schemas import MoveIn, RoomOut

app = FastAPI(title="Игры P58")
rooms: dict[int, dict] = {}

@app.post("/rooms", status_code=201)
def create_room() -> dict:
    room_id = len(rooms) + 1
    rooms[room_id] = {"board": [[0] * 7 for _ in range(6)], "turn": 1}
    return {"room_id": room_id}

@app.get("/rooms/{room_id}")
def get_room(room_id: int) -> RoomOut:
    if room_id not in rooms:
        raise HTTPException(404, detail={"code": "no_room", "message": "Нет комнаты"})
    return RoomOut(room_id=room_id, **rooms[room_id])

Ревью PR агента: чек-лист

  • Совпадают ли пути, поля и коды со спекой? (Сверяем по таблице, не «на глаз».)
  • Есть ли тесты на плохие пути: 404, 409, 422?
  • Нет ли лишнего: эндпоинтов, зависимостей, файлов вне задачи?
  • Нет ли секретов и print отладки?
  • Понимаете ли вы каждую строку? Не понимаете — вопрос в комментарий.
Approve или Request changes
Если хоть один пункт чек-листа не выполнен — Request changes с конкретным комментарием к строке. «Всё плохо» — не ревью.
Измеряем агента
Записываем в таблицу: сколько замечаний на PR, сколько итераций до approve. Это наши первые метрики качества агента.
