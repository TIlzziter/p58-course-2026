Почему не среднее

Запросы, мсСреднееp50p95
20, 20, 20, 20, 20202020
15, 18, 20, 22, 2000415202000
  • Во втором ряду 4 игрока довольны, а один видит «зависание» на 2 секунды.
  • p95 = 200 мс: 95 % запросов быстрее 200 мс, а 5 % — медленнее.
Если в партии 40 ходов, игрок почти наверняка встретит p95 — для него это норма, а не редкость.

Закон Литтла

  • Одновременно в системе: L = λ · W — RPS × время ответа в секундах.
  • 200 RPS и 150 мс → 30 запросов одновременно → нужно 30 воркеров или соединений с базой.
  • Предел одного воркера: 1000 / задержка_мс RPS. 4 воркера по 50 мс — не больше 80 RPS.
При загрузке близкой к 100 % очередь растёт лавиной: задержка взлетает задолго до «полной» мощности. Держим запас 30 %.

class Player(HttpUser):
    wait_time = between(0.5, 2)

    @task(3)
    def rooms(self):
        self.client.get("/api/rooms")

    @task(1)
    def leaderboard(self):
        self.client.get("/api/leaderboard")
  • locust -f locustfile.py --headless -u 200 -r 20 -t 60s --host https://staging…
  • -u — игроков, -r — сколько добавлять в секунду. Растим, пока не появятся ошибки.

Pub/sub в коде

ws.py
async def relay(room_id: str, ws: WebSocket):
    pubsub = redis.pubsub()
    await pubsub.subscribe(f"room:{room_id}")
    async for msg in pubsub.listen():
        if msg["type"] == "message":
            await ws.send_text(msg["data"])

Сколько реплик нужно

  • Замер: одна реплика держит 120 RPS при p95 < 200 мс.
  • Цель демо-дня: 500 RPS, запас 30 % → ceil(500 / (120 · 0.7)) = 6 реплик.
  • Но база одна на всех: 6 реплик × 10 соединений = 60 соединений. Проверяем лимит PostgreSQL.
Масштабирование сдвигает узкое место дальше: с API на базу, с базы на Redis.
