# Лабораторная 15. Античит и rate limit

Клиент — это чужой компьютер: любой может открыть DevTools, поменять JavaScript Mini App и слать на сервер что
угодно. Поэтому сервер проверяет всё, что пришло, и ограничивает частоту запросов. Сегодня: два вида rate limit,
проверка ходов и кликов, чистка секретов в логах, политика для агента (что ему можно запускать) и всё вместе
в FastAPI.

```bash
python check.py           # все задачи
python check.py -v 4      # подробности по задаче 4
```

| Файл | Задачи |
|---|---|
| `ratelimit.py` | 1 `TokenBucket`, 2 `KeyedLimiter` (скользящее окно) |
| `anticheat.py` | 3 `MoveValidator`, 4 `click_audit` |
| `redact.py` | 5 `redact`, `redact_record` |
| `policy.py` | 6 `ToolPolicy` — что разрешено агенту |
| `app.py` | 7* middleware с ограничением и проверка счёта |

Время во всех классах берётся из параметра `now` — функции без аргументов. В тестах её подменяют часами
`FakeClock` (см. `tests/conftest.py`), поэтому тесты не ждут ни секунды.

## Задачи

| № | Что сделать |
|---|---|
| 1 | `TokenBucket`: пополнение `rate` в секунду, но не больше `capacity` (стартовый код копит бесконечно); отказ ничего не списывает; `retry_after`; `cost > capacity` — `ValueError`. |
| 2 | `KeyedLimiter`: окно `(t − window, t]`, отклонённые не записываем (иначе спамер сам себя блокирует навсегда, а память растёт), `retry_after` — когда освободится место; `cleanup` удаляет пустые ключи. |
| 3 | `MoveValidator`: поле, повторы (`stale`), скорость от последней **принятой** точки с допуском 10 % на задержки сети. |
| 4 | `click_audit`: несовпадение счёта, больше `max_cps` нажатий за секунду, слишком ровные интервалы (бот). |
| 5 | `redact`: токены бота, `Bearer`, секретные ключи в `k=v` и JSON, e-mail, телефоны. Регулярки `BOT_TOKEN` и `PHONE` в стартовом коде неверные — тесты покажут почему. |
| 6 | `ToolPolicy.check`: пути через `posixpath.normpath` (стартовый код пропускает `../`), защищённые файлы, цепочки команд в shell, только разрешённые подкоманды git, https и свои хосты. |
| 7* | `create_app`: middleware для `/api/…` с `KeyedLimiter`, ответ 429 и `Retry-After`; ключ — `X-User-Id`, иначе IP; счёт `0..MAX_SCORE` через `Field`. |

## Как это подключается в проекте

* Ключ лимита в настоящем проекте — `user.id` из **проверенного** `initData` (лаба 3), а не заголовок, который
  клиент пишет сам. `X-User-Id` в лабе — упрощение для тестов.
* `KeyedLimiter` в памяти работает, пока процесс API один. При нескольких процессах счётчики хранят в Redis
  (неделя 22): `INCR` + `EXPIRE` на ключ `rl:{user}:{минута}` или сортированное множество.
* `MoveValidator` и `click_audit` вызываются в обработчике WebSocket на каждое сообщение; отклонённый ход не
  применяем, а причину пишем в лог (`redact_record`!) и считаем метрикой `cheat_rejected_total{reason}`.
* `ToolPolicy` — та же идея, что разрешения агента в Cursor и других IDE: список разрешённых команд вместо
  «агент сам разберётся».
