← / → — листать. T — простой / технический режим. A — открыть ответы. G — оглавление. F — полный экран. Esc — закрыть окно.

Переключение режима сохраняет текущий слайд. «Основные» пропускают дополнительные слайды. Полный маршрут — около 88 минут, основной — около 88 минут, включая перерыв.

Файл работает без интернета. Для живых демонстраций нужна сеть. Печать использует выбранный режим, раскрывает ответы и сохраняет один слайд на страницу.

Зачем CI

  • «У меня работает» — главная фраза перед сломанным демо. CI проверяет код на чистой машине.
  • Каждый пуш и каждый PR → одни и те же шаги: линтер, тесты, сборка образа.
  • Красный CI → merge запрещён. Ошибку находит робот за 2 минуты, а не жюри на защите.
  • С агентами это важнее вдвое: агент пишет много кода быстро, и CI — первый, кто его проверяет.

Первый workflow

.github/workflows/ci.yml
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4          # скачать код
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest -q
  • Шаг упал (код возврата не 0) → job красный, следующие шаги не выполняются.

Ловушки YAML

REPL
>>> yaml.safe_load("on: push")
{True: 'push'}                     # YAML 1.1: on/off/yes/no — это булевы значения
>>> yaml.safe_load("v: [3.12, 3.10]")
{'v': [3.12, 3.1]}                 # число! Python 3.1 не существует
>>> yaml.safe_load("v: ['3.12', '3.10']")
{'v': ['3.12', '3.10']}
  • GitHub сам понимает on, но ваш скрипт, читающий workflow, — нет. Это задача 1 лабы.
Версии всегда в кавычках. Ошибка 3.10 → 3.1 встречается в реальных проектах до сих пор.

needs: порядок jobs

lintruff, 30 с
→
testpytest × 2 версии
→
builddocker build
→
mergeразрешён
  • needs: lint — job ждёт успеха lint; если lint красный, test даже не начнётся.
  • Дешёвые проверки — первыми: зачем 3 минуты гонять тесты, если в коде синтаксическая ошибка.
  • Без needs все три job стартуют одновременно — быстрее, но тратят больше минут.

Матрица

strategy:
  fail-fast: false
  matrix:
    python-version: ["3.12", "3.13"]
    os: [ubuntu-latest]
    include:
      - python-version: "3.13"
        experimental: true
steps:
  - uses: actions/setup-python@v5
    with:
      python-version: ${{ matrix.python-version }}
  • Одна job → несколько запусков: декартово произведение значений, затем exclude, затем include.
  • ${{ … }} — выражение; GitHub подставляет значение до запуска шага.

ruff: линтер и форматтер

ruff check .            # ошибки: неиспользуемый импорт, необъявленная переменная, …
ruff check . --fix      # починить, что можно, автоматически
ruff format .           # отформатировать
ruff format --check .   # для CI: только проверить, ничего не менять
  • Настройки — в pyproject.toml, раздел [tool.ruff]: длина строки, набор правил (E F I B UP).
ruff check . || true — заглушить ошибки. Так CI всегда зелёный и ничего не проверяет. Агенты любят этот приём — ищите его на ревью.

Сборка образа

build:
  needs: test
  runs-on: ubuntu-latest
  timeout-minutes: 10
  steps:
    - uses: actions/checkout@v4
    - run: docker build -t game-api:${{ github.sha }} .
  • Собрали образ — значит, Dockerfile не сломан, зависимости ставятся. Публикация образа — на неделе 10.
  • github.sha — хеш коммита: по тегу образа видно, из какого кода он собран.

Защита ветки main

  • *Settings → Branches → Add rule* (или *Rulesets*): main.
  • Require a pull request before merging — пушить в main напрямую нельзя.
  • Require status checks to pass — выбрать lint и test: красный CI блокирует merge.
  • Require approvals: 1 — нужен хотя бы один человек-ревьюер.

Ревью: агент + человек

  • Агент на ревью: «Прочитай diff этого PR. Найди ошибки, непокрытые случаи, лишние изменения. Кода не пиши».
  • Человек: читает diff и ответ агента, проверяет, что PR делает то, что написано в описании.
  • Комментарии — по строкам, конкретные: «здесь None не обработан», а не «плохо».

Когда CI красный

ШагЧто делаем
1открыть упавший шаг и читать лог с первой ошибки, а не с последней
2повторить локально той же командой: ruff check ., pytest -x
3«у меня работает» — сравнить версии Python и зависимостей с CI
4тест мигает — завести задачу, а не жать «Re-run» до зелёного
Чинить CI, отключая проверку или помечая тест skip без задачи, — нельзя.
