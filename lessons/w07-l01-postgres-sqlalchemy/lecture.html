Управление

← / → — листать. T — простой / технический режим. A — открыть ответы. G — оглавление. F — полный экран. Esc — закрыть окно.

Переключение режима сохраняет текущий слайд. «Основные» пропускают дополнительные слайды. Полный маршрут — около 102 минут, основной — около 97 минут, включая перерыв.

Файл работает без интернета. Для живых демонстраций нужна сеть. Печать использует выбранный режим, раскрывает ответы и сохраняет один слайд на страницу.

Зачем база, если есть словарь

  • Словарь в памяти пропадает при каждом деплое, а деплоим мы теперь по несколько раз в день.
  • Файл JSON: две копии сервера пишут одновременно — и одна запись теряется.
  • База данных даёт долговечность, одновременный доступ и проверку данных на своей стороне.
  • SQLite — файл, отлично для тестов и прототипа. PostgreSQL — отдельный сервер для продакшена: много клиентов, строгие типы, надёжные транзакции.

SELECT p.name, p.rating, count(m.id) AS games
FROM players AS p
JOIN matches AS m ON m.player1_id = p.id OR m.player2_id = p.id
WHERE m.played_at > now() - interval '7 days'
GROUP BY p.id
ORDER BY p.rating DESC, games DESC
LIMIT 10;

JOIN
Склеивает строки двух таблиц по условию. Игрок без партий в JOIN не попадёт; чтобы попал — LEFT JOIN.
GROUP BY
Сворачивает строки игрока в одну; count, sum, max считаются по группе.

Индексы

  • Без индекса WHERE tg_id = 51234567 перебирает всю таблицу. С индексом — как поиск по оглавлению.
  • Индекс нужен на колонках из WHERE, JOIN и ORDER BY частых запросов: tg_id, player1_id, played_at.
  • Цена: место на диске и медленнее запись. Индекс «на всё» — плохая идея.
  • Проверка: EXPLAIN ANALYZE SELECT ... — Seq Scan (перебор) или Index Scan.

Рейтинг Эло

  • Ожидаемый счёт A против B: E = 1 / (1 + 10^((Rb − Ra) / 400)). Разница 200 очков — 76 %.
  • После партии: Δ = round(K · (S − E)), S = 1, ½ или 0; у нас K = 32.
  • A получает +Δ, B — −Δ: сумма рейтингов не меняется.

from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

engine = create_async_engine("postgresql+asyncpg://game:secret@db:5432/game")
Session = async_sessionmaker(engine, expire_on_commit=False)

async def main():
    async with Session() as session:
        async with session.begin():            # commit в конце или rollback при ошибке
            session.add(Player(tg_id=51234567, name="Аня"))

Engine
Пул соединений с базой, один на приложение. Создаётся при старте, закрывается await engine.dispose().
Session
«Рабочая тетрадь» одного запроса: копит изменения объектов и отправляет их в базу при flush или commit.

Проблема N+1

  • История из 20 партий: 1 запрос за партиями + 20 запросов за именем соперника = 21 запрос.
  • Один запрос с двумя JOIN к players (через aliased) — и все имена сразу.
p1, p2 = aliased(Player), aliased(Player)
select(Match, p1.name, p2.name).join(p1, Match.player1_id == p1.id).join(p2, Match.player2_id == p2.id)
  • Найти N+1: create_async_engine(url, echo=True) и посчитать SELECT в логе одного запроса.

Миграции Alembic

  • Схема меняется вместе с кодом: новая колонка, индекс. На сервере уже есть данные — drop_all нельзя.
  • Миграция — файл с upgrade() и downgrade(), хранится в git, применяется по порядку.
alembic revision --autogenerate -m "add avatar"   # сравнить модели и базу, написать черновик
alembic upgrade head                              # применить все новые
alembic downgrade -1                              # откатить последнюю
  • В деплое: alembic upgrade head до запуска новой версии приложения.
alembic revision --autogenerate -m "add avatar"   # сравнить модели и базу, написать черновик

autogenerate
Сравнивает модели с базой и пишет черновик. Колонки, индексы и FK видит; CHECK и переименования — нет (переименование выглядит как «удалить и создать» — потеря данных!).
alembic_version
Таблица в базе с номером текущей ревизии. Так Alembic знает, что уже применено.

Ревью миграции

  • Миграцию пишет агент или autogenerate — читает человек: это единственный код, который трогает живые данные.
  • Чек-лист: типы и длины как в моделях; UNIQUE и индексы на месте; downgrade — обратный порядок; нет drop_column с данными без плана.
  • Новая обязательная колонка в заполненной таблице — сначала nullable=True или server_default, потом заполнение, потом NOT NULL.
op.drop_column("players", "rating") в миграции «переименования» — рейтинг всех игроков потерян.
