Зачем ещё одна база

  • PostgreSQL — долгое: игроки, партии, рейтинг. Надёжно, но каждый запрос — диск и транзакция.
  • В игре много короткого: сессии, «кто сейчас в очереди», состояние комнаты, лимиты запросов.
  • Redis — база в памяти: ответ за доли миллисекунды, у каждого ключа может быть срок жизни.
  • Redis общий для всех копий приложения — то, чего не умеет словарь в процессе.

TTL: срок жизни

  • Сессия, комната, лимит — у всего короткого должен быть срок жизни, иначе память кончится.
  • EX при записи или EXPIRE key 60; EXPIRE ... NX — только если срока ещё нет.
  • Скользящий срок: продлеваем при каждом обращении (GETEX key EX 3600) — сессия живёт, пока игрок активен.
  • Фиксированное окно лимита — срок ставим один раз, иначе частые запросы продлевают окно бесконечно.

Атомарность
Команды внутри MULTI/EXEC выполняются подряд, без чужих команд между ними. Если ZREM вернул 0 — соперника уже забрала другая копия.
Расширение окна
Чем дольше ждёт игрок, тем больше допустимая разница: 100, затем +50 каждые 10 секунд — так никто не ждёт вечно.

Pub/sub в коде

events.py
async def publish(r, room_id, message):
    return await r.publish(f"events:{room_id}", json.dumps(message))   # → число подписчиков

async def relay(r, room_id, sockets):
    pubsub = r.pubsub()
    await pubsub.subscribe(f"events:{room_id}")
    async for msg in pubsub.listen():
        if msg["type"] == "message":
            for ws in sockets:
                await ws.send_text(msg["data"])

Без гарантий
Pub/sub не хранит сообщения: кто не был подписан в момент PUBLISH, тот не получит. Поэтому состояние всё равно лежит в hash, а событие — только «смотри, обновилось».
Streams
Если сообщения терять нельзя (журнал ходов), берут XADD/XREAD: поток хранит историю и позволяет дочитать пропущенное.

Rate limit

async def allow(r, key, limit, window):
    async with r.pipeline(transaction=True) as pipe:
        pipe.incr(f"rl:{key}")
        pipe.expire(f"rl:{key}", window, nx=True)
        count, _ = await pipe.execute()
    return count <= limit          # 30 сообщений чата за 10 секунд — дальше 429
  • Защищает от спама в чат, перебора кодов, слишком частых ходов ботом.
  • Ключ — по пользователю из проверенного initData, а не по IP: в школе у всех один IP.

Атомарные операции

  • Двое жмут «присоединиться» одновременно: «прочитал — проверил — записал» в Python даёт гонку.
join.py
async def join(room_id: str, user: int) -> bool:
    seats = f"room:{room_id}:seats"
    if await redis.incr(seats) > 2:  # INCR атомарна
        await redis.decr(seats)      # мест нет — вернуть счётчик
        return False
    await redis.sadd(f"room:{room_id}:players", user)
    return True
  • Redis выполняет команды по одной: INCR атомарна. Несколько команд как одна — MULTI/EXEC или Lua.

Память и вытеснение

  • Redis держит всё в памяти: ключи без TTL копятся, пока память не кончится.
  • maxmemory и политика вытеснения: для чистого кэша — allkeys-lru; для комнат и очереди вытеснение опасно — noeviction (по умолчанию) и TTL на ключах.
  • Смотрим: INFO memory, redis-cli --bigkeys.
Политика вытеснения одна на весь сервер. Кэш и комнаты в одном Redis — выбирайте noeviction и TTL.
