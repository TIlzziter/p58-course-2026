# Лабораторная 20 — заметки для преподавателя

Эталон — файлы этой папки; проверка: скопировать поверх лабы и запустить `python check.py` (≈ 2 с).

* Задача 1 — ротация считается по календарю, а не «последние 7 штук»: при двух бэкапах в день «7 дневных»
  — это 7 дней, а не 3.5. В тесте 120 ночных копий → остаётся 13 (дни и недели/месяцы перекрываются).
  Частая ошибка — недели по `strftime("%W")` вместо ISO-недели: на стыке годов ломается.
* Задача 2 — RPO расписания — **наибольший** промежуток, а не средний: пропущенный ночной бэкап удваивает RPO.
* Задача 3 — главный смысл: `shutil.copy` открытой базы может дать несогласованную копию (в PostgreSQL —
  тем более, файлы данных копировать нельзя). backup API / `pg_dump` дают снимок на момент начала.
  Тест с незакоммиченной вставкой проверяет, что в копию не попадают чужие транзакции.
* Задача 4 — восстанавливаем во временный файл и подменяем `os.replace` только после всех проверок:
  неудачное восстановление не должно добить то, что осталось от рабочей базы. Временный файл — в той же
  папке, иначе `os.replace` между файловыми системами не атомарен.
* Задача 5 — пароль в `argv` виден всем через `ps aux`; поэтому `PGPASSWORD` в env (или `~/.pgpass`).
  `-Fc` — сжатый custom-формат, позволяет `pg_restore -j` и выборочное восстановление.
* Задача 6 — номер строки считаем с 1; `$VAR`, `${VAR}`, `<подсказка>` — не секреты.
* Задача 7* — `corrupt` ломает заголовок SQLite: после него `table_counts` падает, а `restore` всё равно
  работает, потому что пишет новый файл. Обсудить: сколько секунд занял restore на 500 строках и сколько
  займёт на 2 ГБ при 40 МБ/с (задача 2).
* Docker и PostgreSQL в лабе не запускаются — команды проверяются как списки аргументов. На семинаре 26
  те же шаги выполняются на staging по-настоящему.
